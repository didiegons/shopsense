# Assignment 5.4 Reflection: ShopSense Testing & Security

**Most critical bug.** The most serious bug was `POST /api/v1/search` returning HTTP 500, which broke the app's core feature. The surprise was that the code itself was correct: the backend tests passed and the endpoint worked in-process. The running server, however, was a stale Uvicorn process from before I added product images. Its old `Product` model rejected the new `image_url` field in the catalog, and `--reload` had never noticed the change because the project sits in a OneDrive folder. Stopping the stale processes and restarting with polling fixed it without changing any code.

**Most important security issue.** Sending `NaN` as a budget caused a 500 error, and validation errors echoed raw user input back, including a 5 MB query. I fixed both by rejecting non-finite numbers with `allow_inf_nan=False` and by returning validation errors without the echoed input. Eleven new tests prove the fix and confirm that normal searches still behave the same.

**How AI helped.** AI did the repetitive, thorough work: it drove Chrome through every manual test case, captured request bodies to prove filters were applied, sent hostile inputs to the API, and ran axe-core accessibility scans. I reviewed every proposed fix and approved only a narrow set. AI output still needed checking: two of its own test checks were too strict and had to be corrected before the results could be trusted.

**Compared with App #1.** Compared with App #1. My first application, ForensAI, taught me that getting an AI-generated application to work is only the beginning. Much of the testing process involved diagnosing problems after they appeared, including environment-variable loading, API behavior, response parsing, and deployment issues. With ShopSense, I applied those lessons earlier and used a more structured process. Testing was evidence-based and staged: diagnose first, propose a narrow fix, approve the change, re-test it, and document the result. I also relied more heavily on regression tests, security checks, accessibility scans, and measurable pass/fail criteria before deciding that the application was ready. In ShopSense, testing was evidence-based and staged: diagnose first, propose an exact fix, apply it only after approval, then re-test and record the results.

**What I learned.** Passing tests do not prove the running system matches the code. I need to verify the actual environment as well. I also learned that small validation details can turn into security issues, and that accessibility needs both automated scans and measured checks such as contrast ratios and reflow.
